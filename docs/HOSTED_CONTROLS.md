# Hostinger operator controls

The dashboard and sign-in page are `web/index.html`. `web/control.php` accepts authenticated Start/Stop and private order requests. `control_worker.py` runs on the team laptop, polls Hostinger outbound over HTTPS, and starts transcription, desk, and publisher processes. PHP never launches a background process. One hosted installation connects to one team laptop and account, not a separate exchange account per visitor.

## Hostinger setup

1. Use PHP **8.1 or newer**. Upload `web/` as the site's public files. Keep `control_config.php` and its private storage directory **outside** the public web root. On this Hostinger account, File Manager already has `incredible_trades_private` beside `public_html`. Place `control_config.php` in that private directory and set `storage_dir` to `__DIR__`. The PHP process must be able to read and write that folder. If the config location differs from this default, set `CONTROL_CONFIG_PATH` to its absolute path in the server environment.
2. The one-time `web/setup.php` page lets the operator enter a password directly over HTTPS after a separate high-entropy setup key is uploaded to `incredible_trades_private/setup.key`. The page writes only a password hash to the private config and removes the setup key. Do not put the password or its hash in the public files or in Git. Alternatively, copy `control_config.example.php` to the private location and set `password_hash` to a hash generated with `password_hash(..., PASSWORD_DEFAULT)` on a trusted machine. The controls stay disabled until configured. No operator credential is included in this repository. The password fallback can operate dry/demo controls; it cannot authorize LIVE.
3. The active Auth0 Regular Web Application is **MarketPulse Operator Console** in tenant `dev-88yjb6uudqqnsl2d`. Its Authorization Code callback is `https://yellow-boar-756344.hostingersite.com/auth0.php` and its allowed logout URL is the site root. Put `auth0_config.php` in `incredible_trades_private`, never in `public_html` or Git. Set `domain`, `client_id`, `client_secret`, and an `allowed` list of verified operator email addresses. The optional `redirect_uri` must exactly match the Auth0 callback, and `allowed_subjects` can restrict identities further. `live_allowed` is a separate allowlist for LIVE. See `auth0_config.example.php` for the shape, not credentials. An approved Auth0 sign-in has been verified on the hosted site.
4. Set `storage_dir` to an absolute private directory. It holds queued uploads and `control_state.json`. Do not use a directory inside `public_html` or another public web directory.
5. Set `source_hosts` to exact trusted hostnames. The supplied example allows only `www.federalreserve.gov`. The local worker also has `ALLOWED_SOURCE_HOSTS` in `control_worker.py`; keep both lists in sync. Only HTTPS URLs without URL credentials or custom ports are accepted, and the worker rejects private IP resolutions. Review a new host and its redirects/media behavior before adding it. For arbitrary untrusted sources, upload a recording instead.
6. `web/.user.ini` requests `upload_max_filesize=50M`, `post_max_size=52M`, and `max_input_time=120`. Verify the effective values in Hostinger's PHP settings; hosting level limits can override `.user.ini`. The control endpoint independently caps each file at 50 MiB. Adjust the page's displayed limit and the server/Python caps together if a smaller hosting limit is required.
7. Confirm HTTPS is active. The operator session cookie is `Secure` on HTTPS, `HttpOnly`, and `SameSite=Strict`. Run `php -l` on each new PHP file in the deployment environment before enabling access if no local PHP binary is available.

Do not change or expose the existing upload token. The worker reads `hostinger_token.txt` or `HOSTINGER_TOKEN` locally and sends it only in the `X-Upload-Token` header. The browser never receives it. The operator password is a separate credential and must be created by the operator.

## Local worker

Install `requirements.txt`, verify that the existing local API keys and `hostinger_url.txt`/`hostinger_token.txt` are configured, then run `python control_worker.py`. Keep that process running on the local machine. It does not use Streamlit. Its requests are outbound; no inbound laptop port or Hostinger process manager is needed.

The worker accepts validated speaker, quantity, venue, and dry/demo mode choices from the control room. LIVE additionally needs an Auth0 session whose identity is in `live_allowed`, the operator to type `LIVE` when selecting the mode, and the worker process to start with `MARKETPULSE_ALLOW_LIVE=1` in its local environment. Without this local setting, an explicit LIVE request fails before launching a desk process. Analyze jobs always use dry mode even if LIVE is selected elsewhere. A local lock prevents two workers in the same checkout; the process manifest records PID and creation time for crash recovery. Do not run the separate Streamlit audio session or other writers of `live_state.json` at the same time.

Start requires a heartbeat from an online worker. A queued Start expires after 120 seconds, and its private upload is removed. Stop remains queued until the worker acknowledges it, with a three-hour expiry for abandoned commands. The local worker ends any session after two hours. It removes downloaded recording copies on Stop; PHP removes the queued upload after the worker reports stopped or error. Private uploads are also pruned after three hours. If the worker is offline, the page shows that status and disables Start.

Browser recording is not part of these controls. The Upload input accepts an existing recording; it is not a live microphone.

## Orders and keys

The landing page explains which local files hold Gemini, ElevenLabs, Hostinger, optional context, and exchange credentials. Keys never go into the website form or repository. The password fallback can run non-LIVE desk controls but cannot access private exchange snapshots or manual orders.

The Orders tab asks the local worker for the current exchange open orders and positions through authenticated, CSRF-protected jobs. A Buy/Sell ticket sends only venue, environment, market, outcome, quantity, and limit to the local worker. The worker checks a fresh exchange quote and risk limits, and Sell checks verified holdings. It returns a session-bound, single-use preview that expires after 90 seconds. A separate typed `LIVE` and confirmation submits at most once. The worker must have `MARKETPULSE_ALLOW_LIVE=1`, even for manual submissions. A durable request reservation and shared cross-process risk lock apply the $10/order, $50/day, and kill-switch controls to manual and automated orders. A lost exchange response is marked unknown and must be checked directly at the venue before another attempt. Submitted is not equivalent to filled.

The account snapshot and preview results stay in the authenticated private job store. The public state publisher does not include private positions, open orders, or manual attempts. Polymarket Sell stops when the account response does not identify its held side and quantity unambiguously. No real orders are used during deployment verification.
